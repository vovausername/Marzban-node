# Проверка routing на Xray v26.9.9

Дата: 17 ноября 2026. Проверялся Xray `26.9.9 / 52a412d`, Linux amd64.
Это лабораторные замеры, а не измерения на рабочих нодах пользователя.

## Почему прежнюю реализацию удалили

[Marzban-node #17](https://github.com/vovausername/Marzban-node/pull/17) и
[Marzban #737](https://github.com/vovausername/Marzban/pull/737) описывают два
разных дефекта прежнего подхода:

- Неатомарная замена могла очистить routing до ошибки построения новых правил,
  включая служебный маршрут API. Попытка восстановления также могла не успеть.
- Разбор geo-баз при каждой полной замене занимал около 13 секунд на рабочей
  конфигурации и превышал таймаут под нагрузкой.

Нельзя переносить эти замеры на v26.9.9 без повторной проверки. В этой версии
изменился не только алгоритм атомарной замены, но и представление геоданных.

## Что делает v26.9.9

JSON-конфиг преобразуется в protobuf со ссылками на geo-категории. Загрузка
баз и построение geo-матчеров выполняются в работающем ядре. Неизменные
geo-матчеры переиспользуются через кеш:

- [Разбор JSON](https://github.com/XTLS/Xray-core/blob/v26.9.9/infra/conf/router.go)
- [Кеш доменных матчеров](https://github.com/XTLS/Xray-core/blob/v26.9.9/common/geodata/domain_matcher.go)
- [Кеш IP-матчеров](https://github.com/XTLS/Xray-core/blob/v26.9.9/common/geodata/ip_matcher.go)
- [Реестр и обновление геоданных](https://github.com/XTLS/Xray-core/blob/v26.9.9/common/geodata/domain_registry.go)

Следовательно, новый процесс `xray api adrules` сам по себе уже не означает
повторный полный разбор `.dat` при каждой смене списка участников squad.
Кеш использует слабые ссылки; это не обещание бессрочного хранения любых
категорий, когда использующие их правила удалены.

## Сравнение CLI и прототипа protobuf-кеша

Взяты 20 крупнейших по числу доменов категорий из имеющегося `geosite.dat`,
плюс `geoip:cn`, `geoip:us`, `geoip:private`. Список категорий и все измерения
сохранены в JSON рядом с этим документом. Менялись участники одного squad,
базовые правила оставались прежними. По четыре замены на вариант;
таблица содержит медианы времени применения, не задержку пользовательского трафика.

Прототип один раз выполнял `xray convert pb`, затем менял `user_email`
и отправлял полный protobuf через gRPC `AddRule(shouldAppend=false)`.
Проверка `TestRoute` после каждой замены подтверждала добавление одного
участника и удаление другого. Некорректная замена с повторным тегом
отклонена, предыдущие маршруты сохранены.

| Условия | Участники squad | Текущий CLI | Прототип protobuf |
| --- | ---: | ---: | ---: |
| Без дополнительной нагрузки | 200 | 87 мс | 52 мс |
| Без дополнительной нагрузки | 10 000 | 83 мс | 49 мс |
| Одно CPU-ядро с конкурирующей нагрузкой | 200 | 201 мс | 151 мс |
| Одно CPU-ядро с конкурирующей нагрузкой | 10 000 | 237 мс | 194 мс |

Для нагруженного запуска Xray, клиент и отдельный процесс с бесконечным
вычислительным циклом закреплялись на одном доступном CPU через affinity.
Это синтетическая конкуренция за CPU, а не воспроизведение нагрузки рабочих нод.

Первое холодное применение всех этих категорий к ядру с минимальным routing
заняло **3,54 с** без дополнительной нагрузки. Оно успешно прошло с параметрами
PR: RPC timeout 15 с, ограничение процесса 27 с. Холодное применение под CPU-
нагрузкой отдельно не измерялось. Размер protobuf шаблона без больших списков
участников составил 1178 байт, что также подтверждает передачу ссылок на базы.

## Проверка реального обработчика агента и VLESS

Повторён интеграционный тест `routing_sync.sync` с теми же geo-категориями
в базовой таблице, двумя VLESS inbound и локальными outbound-серверами,
возвращающими разные маркеры маршрута:

- Добавление и удаление участников, условия user AND domain, оба inbound.
- Уже открытое соединение сохранило маршрут после удаления участника.
- 10 000 участников, 25 замен, четыре потока новых соединений:
  **7162 правильных ответа, 0 ошибочных маршрутов, 0 ошибок подключения**.
- Повторный `ruleTag` отклонён; прежний маршрут сохранился.

Состав и порядок базовых geo-правил сохранялись во всех заменах, чтобы
проверять именно синхронизацию squad, а не изменение общей конфигурации.

## Решение и границы проверки

Оставить CLI-путь PR #23. Отдельный protobuf-кеш пока не вводится:
экономия в этом тесте составляет десятки миллисекунд, а поддержка нового
транспорта и совместимости схем усложняет агент. Существующие Python protobuf-
схемы панели отличаются от v26.9.9 (в том числе `rule_tag` и геоданные);
исследовательский прототип нельзя переносить в production без обновления схем.

Первое появление новых категорий, изменение самих geo-баз, другой matcher,
медленный диск или более слабая нода могут дать другое время. Атомарность
не гарантирует завершение RPC в заданный срок: таймаут может означать
неопределённый для клиента результат применения. Принудительные таймауты
и восстановление после них этим benchmark не проверялись.

## Сравнение с v26.7.28 на одинаковых данных

Дополнительный тест: одинаковые geo-базы и 20 крупных категорий, 20 одинаковых
замен и 20 изменений состава squad (200 участников) на каждой версии.

| Версия | Повторная замена | Изменение участников | То же под CPU-нагрузкой |
| --- | ---: | ---: | ---: |
| 26.7.28 | 3,13 с | 3,08 с | 9,22 с |
| 26.9.9 | 80 мс | 73 мс | 198 мс |

В v26.7.28 geo-кеш уже существует, однако в этой серии полных замен он
не переиспользовался: 0 HIT, 882 MISS. В v26.9.9: 861 HIT, 21 MISS
(начальная загрузка). Наличие кеша в исходниках само по себе не доказывает
его эффективность при замене таблицы. Исторические 13 секунд на конкретной
рабочей ноде этим тестом не воспроизведены, но замедление старой версии
при полной замене воспроизведено.

Холодное применение: 3,53/3,80 с без нагрузки и 8,90/8,71 с под нагрузкой
для старой/новой версии соответственно. Ускорение относится к повторному
использованию уже загруженных категорий.

Принудительная остановка тестового ядра через SIGSTOP вызвала таймаут
подключения CLI. После SIGCONT маршрут и повторное применение работали
в обеих версиях. Это **не проверка таймаута во время исполнения AddRule**:
неопределённый результат уже принятого RPC этим сценарием не покрыт.
